# ADR 0009. Канал неактивности: флаг, серверный mute и выход из него

- **Статус:** принято (этап 2.3.1, блок D)
- **Дата:** 2026-11-20
- **Связано:** дизайн 4.5, 4.6, 4.7; ADR 0001, ADR 0002

## Контекст

Канал «AFK» до этого этапа был просто одним из двух предсозданных голосовых
каналов (`server/internal/channels`): у него не было никакой семантики, и
вошедший пользователь продолжал публиковать микрофон. Для «ушёл, но остался в
голосовом канале» это неверно: отойдя от компьютера, человек не должен
транслировать комнату или разговоры в ней.

Определять такой канал по имени нельзя: имя видно пользователю, его можно
переименовать, локализовать или просто удалить. Имя — не контракт. Нужен
признак в данных и серверная проверка: клиентский auto-mute обходится любым
клиентом и не является решением, потому что права проверяются на сервере.

## Решение

### Флаг, а не имя

Идли-канал (канал неактивности) — это канал с флагом:

- `Channel.afk` в `proto/rostalk/v1` (новое поле с тегом 12);
- столбец `channels.afk` (миграция `0003_channel_afk.sql`, `NOT NULL DEFAULT 0`);
- `channels.Channel.AFK` на сервере и `ChannelView.afk` в ядре клиента и UI.

Сервер нигде не сравнивает имя канала. Канал с флагом остаётся обычным
голосовым каналом: в нём слышно других, но говорить нельзя. Несколько каналов
могут быть помечены одновременно — каждый из них мьютит своих участников.

Совместимость: это новое поле proto3 `bool` со значением по умолчанию `false`,
поэтому версия протокола не повышается (правила в `protocol.proto`). Старый
клиент увидит такой канал как обычный, но сервер всё равно не выдаст ему права
публикации. Старый сервер не присылает поле, и новый клиент считает канал
обычным.

### Миграция существующих баз

`0003_channel_afk.sql` добавляет столбец с `DEFAULT 0` — существующие строки
остаются валидными. Одноразовый `UPDATE ... WHERE name = 'AFK'` помечает канал,
который создавал bootstrap прошлых версий: до миграции флага не существовало, и
имя по умолчанию было единственным способом его узнать. Без этого после
обновления существующей базы канал остался бы без флага, а админ-экрана каналов
до этапа 3.2 нет. После миграции имена не читаются нигде.

При первом запуске флаг ставится каналу, который создаёт bootstrap. Имя
«AFK» остаётся только текстом, который видит пользователь.

### Вход в канал неактивности

После успешного перемещения сервер:

1. запоминает текущее значение `self_muted` пользователя (для возврата);
2. выставляет `self_muted = true` через существующий `state.Hub.SetVoiceState` —
   всем клиентам уходит `UserUpdated`, и индикатор микрофона загорается у всех;
3. вызывает существующий `media.Backend.SetCanPublish(room, "<id>:voice", false)`.
   Если участник ещё не подключился к комнате, бэкенд отвечает `ErrNotFound` —
   это не ошибка: токен, выданный на этот вход, уже не содержит `canPublish`.

Последние два пункта — независимые барьеры. Токен закрывает публикацию с самого
начала, `SetCanPublish` останавливает уже подключённого участника (например,
переподключение в пределах grace-периода, когда старая медиа-сессия ещё жива).
`IssueToken` для канала с флагом не выдаёт `canPublish`, даже если право
`PERMISSION_SPEAK` есть.

Клиент не может снять этот mute: `SetVoiceState` с `self_muted = false` в таком
канале отклоняется ошибкой `ERROR_CODE_REJECTED`, и состояние остаётся
выключенным. UI блокирует кнопку микрофона и показывает причину, но это лишь
удобство: решение принимает сервер.

### Выход, перемещение и возврат

- Выход из канала, перемещение в любой другой канал и удаление канала
  восстанавливают `self_muted` в значение, которое было до **первого** входа в
  канал неактивности. Пользователь, который был замьючен сам, остаётся
  замьюченным; пользователь, который говорил, снова говорит.
- Выход и перемещение удаляют старого медиа-участника и выдают новые креды для
  нового канала: `canPublish` возвращается, если есть право говорить и нет
  серверного mute модератора (этап 3.1). AFK-mute и moderator-mute — разные
  состояния: выход из канала неактивности не снимает наказание модератора.
- Повторный вход в канал неактивности снова выключает микрофон.
- Обрыв связи: присутствие исчезает вместе с сессией, запомненное значение
  забывается. Новое подключение начинает с пустого присутствия и не наследует
  AFK-mute.
- Если флаг поставить или снять у занятого канала (серверный `UpdateChannel`;
  в 3.2 это будет админ-экран), политика применяется к находящимся в нём сразу:
  при установке — mute и `canPublish=false`, при снятии — восстановление
  микрофона и `canPublish=true`, если пользователь не замьючен модератором.

Клиент при этом остаётся клиентом: он показывает состояние и блокирует
бесполезную кнопку, но не решает, можно ли публиковать.

### Клиент

- `ChannelView.afk` доходит до UI через ядро. Дерево каналов показывает значок
  канала неактивности (в i18n — по смыслу флага, без привязки к имени), а панель
  управления блокирует микрофон с подсказкой, пока пользователь в таком канале.
- Состояние «микрофон выключен» приходит с сервера в `VoiceState.self_muted`;
  клиент его не выдумывает.
- Оболочка Tauri зеркалит серверный `self_muted` своего пользователя в локальный
  голосовой движок (`set_self_muted`) при снапшоте и событиях о себе. Это
  останавливает и захват, а не только публикацию. Медиа-плоскость всё равно
  отказывает в публикации, так что зеркало — не проверка прав, а согласованность
  состояния.

## Последствия

- Вход и выход дают по одному дополнительному `UserUpdated`; порядок событий
  остаётся согласованным (перемещение, затем флаги), снимок всегда актуален.
- `SetCanPublish(false)` вызывается синхронно в обработчике входа. Недоступность
  медиа-бэкенда не отменяет вход: ошибка логируется, а токен всё равно без
  `canPublish`.
- Флаг живёт в базе и переживает перезапуск; снимок и `ChannelUpdated` несут его
  клиентам.
- Откат клиента 2.3.1d на предыдущую версию безопасен: поле игнорируется, но
  серверный mute остаётся в силе.
- Тесты сервера: вход прекращает публикацию, выход/возврат ведёт себя по
  решению выше, собственная настройка mute не теряется, снять mute запросом
  нельзя, другие каналы и другие пользователи не затронуты, установка флага на
  занятый канал применяется сразу, миграция существующей базы сохраняет строки
  и помечает только исторический канал.
- Ручная проверка: войти в канал неактивности — индикатор микрофона выключен,
  бот/собеседник не получает звук; выйти — прежнее состояние микрофона
  вернулось.

## Альтернативы

- **Определять по имени канала.** Ломается при переименовании и локализации,
  завязывает логику на отображаемый текст. Отклонено.
- **Только клиентский auto-mute.** Обходится любым клиентом; «все проверки прав —
  на сервере». Отклонено.
- **Только `self_muted` без `canPublish=false`.** Клиент может не применить флаг
  и продолжить публикацию. Отклонено.
- **Отдельный `ChannelKind.AFK`.** Смешивает ортогональные свойства: канал
  неактивности остаётся голосовым и должен работать как голосовой для
  прослушивания. Отклонено.
- **Всегда снимать mute при выходе.** Проще, но стирает собственную настройку
  пользователя, который замьютил себя до AFK. Отклонено.
