# ADR 0003. Движок стримов: WebView2 + livekit-client

- **Статус:** предварительно принято, есть непроверенные пункты (этап 0.3)
- **Дата:** 2026-11-19
- **Проверял:** spike `spikes/stream-webview`

## Контекст

Дизайн (разделы 4.3, 5.3, 9) предлагает два пути демонстрации экрана:

- **WebView:** `getDisplayMedia` + `livekit-client` внутри Tauri. Даёт
  аппаратное кодирование средствами WebView2, выбор источника штатным
  диалогом и минимум своего кода.
- **Нативный:** `DesktopCapturer` из `libwebrtc`, публикация из Rust, просмотр
  в отдельном окне на `wgpu`.

Риски, которые надо было проверить: работает ли `getDisplayMedia` в WebView2,
доступен ли системный звук, разрешён ли `ws://127.0.0.1` из страницы Tauri,
какой кодировщик выбирается и как ведёт себя окно при сворачивании.

## Что сделано

`spikes/stream-webview`:

1. **`ui/`** — React + TypeScript + Vite + `livekit-client` 2.24.1.
   - издатель: `getDisplayMedia` (видео + попытка захватить системный звук),
     пресеты 720p30 / 1080p30 / 1080p60, simulcast, публикация
     `screen_share` и `screen_share_audio`;
   - зритель: подключение, подписка на `screen_share`, `<video>`;
   - оверлей статистики из `getRTCStatsReport`: кодек,
     `encoderImplementation`/`decoderImplementation`, разрешение, fps,
     битрейт, `qualityLimitationReason`, `powerEfficientEncoder`;
   - `window.__spike` — машиночитаемое состояние для теста.
2. **`proxy/`** — Rust-библиотека loopback-прокси: слушает
   `ws://127.0.0.1:<случайный порт>`, идёт на `wss://<шлюз>/rtc` через rustls,
   сверяет SHA-256 отпечаток сертификата и пересылает WebSocket-кадры без
   разбора. Есть CLI и unit-тест пересылки.
3. **`src-tauri/`** — оболочка Tauri 2 с командой `start_proxy`; UI в режиме
   `?proxy=1` получает порт через IPC и подключается к `ws://127.0.0.1:<port>`.
4. **`tests/stream.spec.ts`** — Playwright: два независимых контекста Chromium,
   издатель и зритель, против настоящего встроенного LiveKit (spike 0.1).
   Подставной источник экрана — флаги Chromium
   (`--auto-select-desktop-capture-source`, `--use-fake-ui-for-media-stream`).

## Проверено

### Сквозной стрим в Chromium (Windows, headless)

Тест проходит: издатель публикует, зритель получает дорожку
`screen_share`, статистика обновляется.

| Пресет | Кодек | Кодировщик | Захват | Битрейт издателя | Зритель |
|---|---|---|---|---|---|
| 1080p30 | VP8 | `libvpx` (SW) | 960×540 @ ~21 fps | ~2.1 Мбит/с | 960×540 @ ~19 fps, ~2.0 Мбит/с |
| 720p30 | H.264 | `OpenH264` (SW) | 1280×720 @ ~6 fps | ~1.3 Мбит/с | 640×360 @ ~20 fps |
| 1080p30 | H.264 | `OpenH264` (SW) | 1920×1080 @ ~2 fps | ~0.6 Мбит/с | 960×540 @ ~20 fps |
| 1080p60 | H.264 | `OpenH264` (SW) | источник 960×540 | 0 в статике | 960×540 @ ~20 fps, ~5.4 Мбит/с |

Выводы:

- `getDisplayMedia` и simulcast в Chromium работают; кадры доходят через наш
  шлюз и UDP-медиа.
- В headless Chromium оба кодека — **программные**. Аппаратного кодировщика
  в этом окружении нет, поэтому вопрос «H.264 через Media Foundation или VP9»
  здесь не решается.
- Низкий fps H.264 (2–6) объясняется подставным статичным источником и
  software-кодировщиком; на реальном экране и WebView2 это надо перемерить.
- Грубая оценка CPU: весь браузер (издатель + зритель) на прогоне 1080p60
  H.264 занял **~2.4 % от 12 логических ядер** (~29 % одного ядра). Цифра
  включает декодирование у зрителя и software-кодирование.

### Loopback-прокси

`cargo test` для `proxy/` проходит два теста: пересылка кадров через
plain-ws и полный TLS-путь с самоподписанным сертификатом и пином листа.
Пиннинг реализован через `rustls::ServerCertVerifier` (сравнение SHA-256 DER);
проверка подписи TLS 1.2/1.3 делегируется `rustls`. Криптопровайдер (`ring`)
устанавливается явно: иначе rustls не может выбрать его автоматически, когда в
зависимостях оказываются и `ring`, и `aws-lc-rs`.

## Не проверено (и почему)

На этой машине **нет MSVC Build Tools**, поэтому Tauri-приложение под Windows
не собиралось. Без этого нельзя честно ответить на главные вопросы этапа:

| Вопрос | Статус |
|---|---|
| Работает ли `getDisplayMedia` в WebView2 и как выглядит выбор источника | Не проверено |
| Доступен ли системный звук в WebView2 | Не проверено; UI пробует `audio:true` и откатывается на видео без звука |
| Разрешён ли `ws://127.0.0.1` со страницы `tauri://localhost` | Ожидаемо да (loopback — trustworthy origin, CSP разрешает), но не проверено в WebView2 |
| Аппаратный или программный кодировщик в WebView2 | Не проверено; в headless Chromium — программный |
| Поведение при сворачивании окна | Не проверено |
| CPU стримера/зрителя на пресетах | Только грубая оценка в Chromium, см. выше |

Ручной чек-лист для машины с Visual Studio Build Tools и WebView2:

1. `npm --prefix spikes/stream-webview/ui ci && npm --prefix spikes/stream-webview/ui run build`
2. `cd spikes/stream-webview && npm ci && npx tauri dev` (или `cargo tauri dev`).
3. Открыть окно, нажать «Начать стрим»: появляется ли системный диалог выбора
   экрана/окна, можно ли выбрать окно и включить системный звук.
4. Проверить оверлей: кодек, `encoderImplementation`, разрешение, fps.
   Ожидаемые ориентиры: 720p30 ~2.5 Мбит/с, 1080p30 ~4, 1080p60 ~6–8.
5. Запустить `?proxy=1&token=...&fp=...` в Tauri-окне: подключение должно идти
   через `ws://127.0.0.1:<port>` и не падать на самоподписанном сертификате.
6. Свернуть окно на 30 секунд: продолжается ли публикация, не растёт ли CPU.
7. Сравнить с `examples/screensharing` из rust-sdks на той же машине: какой
   кодировщик и CPU на 1080p30.

## Решение (предварительное)

**Основной путь на Windows — WebView2 + `livekit-client`**, как в дизайне.
Причины: движок уже работает в Chromium, UI переиспользуется, а нативный путь
требует своего окна на `wgpu` и ручного выбора источника.

Но этап 5.1 нельзя считать закрытым, пока не пройден ручной чек-лист выше.
Критерии перехода на запасной нативный путь:

- `getDisplayMedia` в WebView2 не отдаёт видео или не показывает выбор окна;
- нет системного звука и обход через WASAPI process loopback невозможен;
- аппаратное кодирование недоступно и software не держит 1080p30 на целевом
  железе;
- `ws://127.0.0.1` блокируется политикой WebView2.

| Платформа | Основной путь | Запасной |
|---|---|---|
| Windows (MVP) | WebView2 + livekit-client | нативный захват `DesktopCapturer` + окно `wgpu` |
| macOS | не в MVP; вероятно, тот же WebView | нативный |
| Linux | не в MVP; WebKitGTK + тот же UI | нативный |
| Браузер (после MVP) | livekit-client напрямую | — |

## Последствия

- Этап 5.1 начинается с прогона ручного чек-листа; если он зелёный —
  реализуем WebView-путь и не пишем нативный.
- Этап 5.2 (звук приложения) остаётся нужен в любом случае: системный звук
  WebView2 тащит голоса из чата.
- Локальный прокси — общий компонент для стримов и файлов/картинок
  (этап 4.1); его API (`start_proxy(url, fingerprint) -> port`) уже готов.
- CSP Tauri должен разрешать `ws://127.0.0.1:*` и `media-src blob:`; это
  зафиксировано в `src-tauri/tauri.conf.json`.

## Как воспроизвести тест

```powershell
# сервер spike 0.1 с LAN IP хоста (см. ADR 0001), затем:
cd spikes/stream-webview
npm ci
npm --prefix ui ci
npm --prefix ui run build
npm --prefix ui run preview         # терминал 1

$env:SPIKE_SERVER="wss://localhost:7443"
$env:SPIKE_PRESET="1080p30"
$env:SPIKE_CODEC="h264"
npx playwright test tests/stream.spec.ts
```
