# ADR 0021. Установка сервера из клиента по SSH

- **Статус:** принято (этап 6.1a); п. 4 и 5 заменены ADR 0026 (P13): мастер
  и серверный бандл переехали из клиента в отдельное приложение
  `rostalk-server-setup`
- **Дата:** 2026-11-21
- **Связано:** дизайн 7; ADR 0001, 0015, 0017; `docs/IMPLEMENTATION_PLAN.md` 6.1 (пункт 8), 6.1a

## Контекст

Требование владельца: сервер должен ставиться из клиента, без терминала. На
экране подключения рядом с «Подключиться» нужна вторая равноправная кнопка
(«Свой хостинг»), после которой пользователь вводит адрес VPS и учётные данные,
выбирает настройки, а клиент сам ставит сервер и подключает пользователя.

Пункт 8 этапа 6.1 («Установка из клиента») был в плане, но не реализован:
6.1 закрыл только CLI-установку. Хостингового CI и серверного хостинга нет
(ADR 0015), поэтому клиент не может рассчитывать на скачивание с GitHub —
серверные бинарники должны ехать вместе с клиентом.

Ограничение античита: клиент не трогает локальный файрвол, службы и чужие
процессы. Здесь речь идёт о **удалённой** машине по SSH — это разрешено, но
только в границах установки RosTalk и с явным подтверждением.

## Решение

### 1. SSH-клиент

- Библиотека — `russh` (чистый Rust, async/tokio, без C и OpenSSL; пароли
  зачищаются в `Drop`). Версия пинована; API сверяется с docs.rs закреплённой
  версии. Крипто-бэкенд — `ring` (уже в дереве), не `aws-lc-rs`, чтобы не
  тащить CMake/NASM в сборку клиента.
- Альтернатива `ssh2` отклонена: C-зависимость, vendored OpenSSL, лишняя
  поверхность для антивирусов.
- Передача файлов — не SFTP, а tar-поток в `exec`-канал
  (`tar -xzf - -C <tmp>`), чтобы не добавлять `russh-sftp`. Бинарник и
  `install.sh` кладутся во временный каталог, после установки удаляются.
- Все команды собираются как argv и экранируются; пароль и ключи никогда не
  попадают в командную строку, логи, события UI или отчёты об ошибках.

### 2. Проверка хоста и вход

- Host key — TOFU: первый коннект отклоняется, клиент показывает SHA-256
  отпечаток ключа, пользователь подтверждает; отпечаток сохраняется в
  `ssh_known_hosts.json` в каталоге приложения. Несовпадение — жёсткая ошибка
  с объяснением (возможен MITM или переустановка VPS), без опции «продолжить
  молча».
- Способы входа: приватный ключ (файл OpenSSH + опциональная парольная фраза)
  — предпочтительный; пароль — явный выбор пользователя (в т.ч. для
  `keyboard-interactive`); root или пользователь с sudo.
- Пароль живёт только в памяти на время операции и зачищается. По умолчанию не
  сохраняется. Галочка «запомнить» кладёт секрет в Windows Credential Manager
  (существующий `keyring`-путь), путь к ключу — в настройки, содержимое ключа —
  никогда.
- sudo: если пользователь не root, команды идут через `sudo -S` с паролем на
  stdin; поддерживается отдельное поле «пароль sudo», если он отличается.
  Sudoers и SSH-ключи на сервере не меняются.

### 3. Что клиент делает на удалённой машине

Только установка и обслуживание RosTalk:

1. Preflight: `uname -m` (amd64/arm64), `/etc/os-release`
   (ubuntu/debian/fedora/almalinux/rocky/rhel/ol/centos), наличие systemd,
   `sha256sum`, `tar`, `openssl` (при отсутствии — установка пакета), свободное
   место, занятость портов 7443/7881/7882, доступ к `https`-портам.
   Неподдерживаемая система —
   понятная ошибка до любых изменений.
2. Загрузка: tar с `rostalk-server`, `install.sh`, `SHA256SUMS`,
   `SHA256SUMS.sig`, `release.pub`; **локальная** проверка SHA-256 и подписи
   Ed25519 встроенным публичным ключом релиза до отправки; затем `install.sh
   --from-file --sums` проверяет ещё раз на месте. На OpenSSL 1.1.1
   (`pkeyutl -rawin` отсутствует, например AlmaLinux 8) `install.sh` получает
   от клиента флаг `--preverified-signature`, проверяет SHA-256, явно
   предупреждает, что Ed25519 уже проверен клиентом, и продолжает. Без этого
   флага проверка подписи не пропускается.
3. Установка: `install.sh` создаёт пользователя, каталог данных, systemd-юнит
   (уже hardened в 6.1), запускает сервис и печатает админ-ссылку.
4. Файрвол: по умолчанию клиент **не** меняет его, а показывает точные
   команды для ufw/firewalld и напоминает про файрвол облака. Отдельная
   галочка «открыть порты» выполняет ровно три правила (7443/tcp, 7881/tcp,
   7882/udp) на удалённой машине после предпросмотра. Если файрвол не
   установлен или не активен, установка не прерывается: клиент показывает
   предупреждение и команды для ручного открытия. Локальный файрвол Windows не
   трогается никогда.
5. После установки: `rostalk-server invite --public-host … --role Admin`
   выполняется по SSH, ссылка парсится и показывается; клиент сохраняет
   закладку (host + fp) и сразу подключается. Для друзей — вторая ссылка с
   ролью Member.
6. Домен (необязательно): поле «домен» → `install.sh --domain`; клиент
   проверяет, что A/AAAA домена указывает на этот VPS, и предупреждает, что
   нужны 80/443. Без домена ссылки содержат `fp` (ADR 0001).
7. Повторный запуск: если RosTalk уже стоит, мастер предлагает «обновить» или
   «переустановить»; перед переустановкой делается
   `rostalk-server backup` в `/var/backups/rostalk`, каталог `/data` не
   удаляется. Обновление — только подписанным бинарником.
8. Откат: предыдущий бинарник и юнит сохраняются как `.bak`; если сервис не
   поднялся или `/healthz` не отвечает, клиент возвращает `.bak`, перезапускает
   службу и показывает `journalctl -u rostalk-server` (без секретов).

### 4. Бинарники в составе клиента

- `make release-client` сначала собирает серверные бинарники linux/amd64 и
  linux/arm64 из того же коммита (`deploy/release.sh`, подпись), затем кладёт
  их в ресурсы установщика. Версия клиента и сервера совпадают.
- Обе архитектуры включены: у пользователя нет способа скачать нужную
  отдельно. Ориентировочная цена — +40–50 МБ к установщику; это принято.
- В dev-сборке путь к каталогу с бинарниками задаётся
  `ROSTALK_SERVER_BUNDLE`; в релизе — `resource_dir()/server/`.

### 5. UI

Два равноправных действия на экране подключения: **«Подключиться»** (ссылка
или адрес) и **«Свой хостинг»** (мастер). Мастер:

1. «Сервер»: адрес/IP, SSH-порт (22), пользователь, способ входа, ключ/пароль,
   отпечаток host key.
2. «Проверка»: сводка preflight и настройки — имя сервера, домен (опц.), режим
   входа (invite/password), лимит онлайна, порты, галочка «открыть порты».
3. «Установка»: пошаговый прогресс и журнал без секретов, кнопка «Отмена».
4. «Готово»: админ-ссылка (сразу «Подключиться»), ссылка для друзей, памятка
   про порты облачного файрвола.

Все строки — i18n (ru/en), ошибки — человеческим текстом, анимации
transform/opacity ≤150 мс. UI не ходит в сеть: только IPC ядра.

### 6. Тесты

- Юнит: сборка и экранирование команд, sudo/root, отпечаток host key,
  парсинг ссылки, матрица distro/arch, красная блокировка секретов в логах,
  идемпотентность и выбор «обновить/переустановить».
- Интеграция: контейнер ubuntu:24.04 с sshd на localhost:2222, вход по паролю
  и по ключу; неправильный пароль, несовпадение host key, занятый порт,
  неподдерживаемая ОС; полный цикл установка → healthz → invite → подключение
  клиента; повторная установка не теряет данные. `install.sh` отдельно
  проверяется в ubuntu/debian/fedora/almalinux:8/rockylinux:9, включая fallback
  подписи на OpenSSL 1.1.1.
- UI: vitest на состояния мастера и ошибки; Playwright-скриншоты в
  `docs/assets/stage-6.1a`.

## Последствия

- Клиент получает SSH-поверхность (russh) и обязан хранить секреты только в
  памяти/ Credential Manager; ревью безопасности обязательно.
- Установщик клиента растёт на размер двух серверных бинарников.
- Сборка клиента зависит от кросс-сборки сервера; `make check` остаётся
  быстрым, потому что бандл нужен только для релизной упаковки.
- Возможные ограничения: провайдерский файрвол (Hetzner/OVH) из SSH не
  открыть — клиент показывает чек-лист; экзотические дистрибутивы не
  поддерживаются, установка честно откажется.
- Откат: убрать пункт «Свой хостинг» и модуль SSH; сервер и данные не
  затрагиваются.
