# ADR 0001. Медиа-бэкенд: встроенный LiveKit

- **Статус:** принято (этап 0.1)
- **Дата:** 2026-11-19
- **Проверял:** spike `spikes/embed-livekit`

## Контекст

По дизайну (разделы 3, 4.1, 9) сервер — один Go-бинарник, внутри которого
работает SFU. Проверить нужно было четыре вещи:

1. LiveKit Server действительно запускается как библиотека, а не только как
   отдельный процесс.
2. Сборка проходит с `CGO_ENABLED=0` под `linux/amd64` и `linux/arm64`.
3. Звук ходит через наш HTTPS/WSS-шлюз на `:7443` и UDP-порт `7882`.
4. Габариты (бинарник, RSS, CPU, старт) позволяют уложиться в бюджеты
   раздела 6 дизайна.

## Что сделано

`spikes/embed-livekit` — Go-программа, которая:

- генерирует конфиг LiveKit в памяти и запускает его в том же процессе
  (`config.NewConfig` → `routing.NewLocalNode` → `prometheus.Init` →
  `service.InitializeServer` → `server.Start`);
- поднимает HTTPS/WSS на `:7443` с долгоживущим сертификатом: собственный CA
  (ca.pem) и подписанный им лист, SHA-256 отпечаток листа печатается и
  переживает перезапуск;
- проксирует `/rtc` на loopback-сигналинг LiveKit;
- отдаёт `/dev/token` — **только для прототипа**, чтобы headless-участники и
  UI получали токены без control plane;
- `cmd/probe` — headless-участники на `server-sdk-go`: публикуют тон 440 Гц
  (PCMU, чтобы не тащить CGO-энкодер) и считают принятые RTP-пакеты.

Сервер собран в Docker-образ (`spikes/embed-livekit/Dockerfile`), порты
`7443/tcp`, `7881/tcp`, `7882/udp` опубликованы. Для измерений — отдельный
`bench/compose.yaml` с фиксированной сетью, чтобы клиент не попадал в cgroup
сервера.

## Результаты

### Встраивание и сборка

| Проверка | Результат |
|---|---|
| Запуск в одном процессе | Работает: `service.InitializeServer` + `server.Start`, без Redis |
| `CGO_ENABLED=0 linux/amd64` | Собирается, бинарник **54.4 МБ** (strip) |
| `CGO_ENABLED=0 linux/arm64` | Собирается, бинарник **50.8 МБ** (strip) |
| Старт до готовности шлюза | **16–46 мс** в процессе, 125 мс в холодном контейнере |
| Отпечаток сертификата после перезапуска | Не меняется (ключ и сертификат лежат в `/data`) |

### Медиа

| Сценарий | Результат |
|---|---|
| 2 издателя + 2 подписчика внутри контейнера | Каждый подписчик получил по 505 пакетов (80.8 КБ) от каждого издателя за 12 с |
| 2 + 2 в двух контейнерах одной Docker-сети | 506 пакетов от каждого издателя, потери в пределах старта |
| Клиент на Windows-хосте через опубликованные порты, `node_ip=127.0.0.1` | **Не работает.** Pion собирает кандидатов только на LAN-интерфейсах и не может отправить пакет с `172.19.0.1` на `127.0.0.1` (`wsasendto: A socket operation was attempted to an unreachable network`) |
| То же, `rtc.force_tcp=true` | TCP-кандидат `127.0.0.1:7881` в SDK-пробе тоже не соединился (нет локальной пары) |
| Клиент на Windows-хосте, `node_ip=<LAN IP хоста>`, `enable_loopback_candidate=false` | **Работает по UDP**: 650/643 пакета на каждого издателя за 15 с |
| `node_ip=<LAN IP>`, `enable_loopback_candidate=true` | STUN-пакеты доходят до контейнера, но LiveKit не отвечает: mux привязан к адресу интерфейса, а агент ищет mux по анонсированному IP |

Опубликованный UDP-порт сам по себе исправен: эхо-контейнер на `7999/udp`
принимает датаграммы и с `127.0.0.1`, и с LAN IP. Проблема именно в выборе
локального адреса ICE, а не в пробросе портов Docker Desktop.

### Нагрузка (Docker Desktop, Linux-контейнер, x86_64)

Методика: N издателей публикуют PCMU 50 пакетов/с, M подписчиков подписаны на
всех; сервер только пересылает. CPU — `usage_usec` cgroup сервера / время;
память — `memory.current`.

| Сценарий | Потоков к подписчикам | CPU (одно ядро) | RSS/peak | Простой |
|---|---|---|---|---|
| Без клиентов | 0 | 0.4–0.9 % | 12–13 МБ | — |
| 10 участников (9 издателей + 1 подписчик) | 9 | **18.6 %** | 37.5 МБ | — |
| 30 участников (29 + 1) | 29 | **32.1 %** | 79.7 МБ | — |
| 34 участника (29 + 5) | 145 | **51.2 %** | 114.1 МБ | — |

**Оговорки, без которых цифры нельзя сравнивать с разделом 6:**

- Это Docker Desktop на Windows: виртуальная машина добавляет накладные
  расходы и искажает CPU. Бюджет «10 человек < 10 % одного ядра» здесь **не
  подтверждён** (18.6 %), но и нагрузка не эквивалентна: в реальном канале
  из 10 человек каждый подписан на 9 других (90 потоков), а не 9.
- Абсолютные значения CPU на реальном Linux нужно перемерить на этапе 7.1.
- 145 потоков при 51 % CPU дают верхнюю оценку стоимости пересылки: примерно
  0.35 % ядра на поток в этом окружении. Для 15 человек в канале (210
  потоков) это ~70 % ядра — на границе; на реальном железе ожидаем заметно
  меньше, но это надо проверить.
- Память в бюджеты укладывается с запасом: < 150 МБ в простое и < 250 МБ
  при 10–30 участниках.

## Обнаруженные ловушки

1. **`replace` в go.mod зависимостей игнорируются.** LiveKit Server собирается
   только если повторить в своём модуле три замены:
   `pion/webrtc/v4 → livekit/webrtc-pion/v4 v4.2.18-warp.7`,
   `pion/dtls/v3 → livekit/dtls/v3 v3.1.5-warp.3`,
   `pion/ice/v4 → livekit/ice/v4 v4.4.0-warp.3`.
2. **Версии форков LiveKit Server и server-sdk-go несовместимы в одном
   модуле.** Server требует `ice v4.4.0-warp.3`, SDK — `v4.4.8-warp.4`;
   `go mod tidy` выбирает одну версию и сборка падает. Поэтому probe вынесен
   в отдельный Go-модуль `spikes/embed-livekit/probe` со своими `replace`.
   В `server/internal/media` SDK не понадобится, а `rostalkctl` будет отдельным
   модулем/зависимостью — это надо учесть на этапе 1.1.
3. **`prometheus.Init` обязателен при встраивании.** Без него фоновый
   `NodeStats` падает с nil pointer (`hwstats.MemoryStats` не создан).
   В `cmd/server` это делает CLI, при встраивании легко забыть.
4. **`enable_loopback_candidate` нельзя включать вместе с не-loopback
   `node_ip`.** В этой версии это ломает сопоставление UDP-mux: STUN приходит,
   ответа нет. Для Docker/LAN его нужно выключать, для тестов внутри
   контейнера — включать.
5. **Docker Desktop и `node_ip=127.0.0.1`.** Клиент на хосте не может открыть
   медиа на loopback: ICE-сокет привязан к LAN-адресу. Рабочая схема для
   разработки на Windows — анонсировать LAN IP хоста
   (`--advertise-ip <ip>`), а не `127.0.0.1`. Это отклонение от дизайна
   (раздел 4.1/7), зафиксировано здесь; на этапе 1.4 нужно поддержать флаг и
   печатать ссылку с этим хостом.
6. **`/dev/token` — дыра.** В прототипе он выдаёт токены без аутентификации.
   В сервере такого эндпоинта быть не должно: токены выдаёт control plane после
   проверки прав (этап 1.4).
7. **Go и rustls по-разному относятся к самоподписанному сертификату.**
   Сертификат с `IsCA=true`, используемый как серверный лист, Go принимает, а
   rustls/webpki отклоняет (`CaUsedAsEndEntity`). Поэтому сервер генерирует
   отдельный CA и лист, подписанный им; клиент доверяет CA (или пинит отпечаток
   листа). Это надо повторить в `internal/netutil` на этапе 1.2.

## Решение

**Вариант A: LiveKit Server как библиотека в процессе `rostalk-server`.**
Дочерний процесс (`go:embed`) не нужен: сборка и запуск работают, накладные
расходы на IPC и второй бинарник не оправданы. Свой SFU на Pion оставляем
запасным вариантом за интерфейсом `MediaBackend`, как и планировалось.

Обязательные условия:

- версии LiveKit Server и Pion-форков фиксируются в `go.mod` и обновляются
  осознанно, с прогоном spike;
- `MediaBackend` — единственное место, где упоминается LiveKit;
- CI собирает сервер под `linux/amd64` и `linux/arm64` с `CGO_ENABLED=0`;
- для dev на Windows: `--advertise-ip <LAN IP>` и
  `enable_loopback_candidate=false`; проверка медиа с хоста — обязательная
  часть `make dev-server-docker`.

## Последствия

- Образ сервера будет ~55 МБ без сжатия; это приемлемо.
- Обновление LiveKit — отдельная задача с прогоном этого spike: два форка
  Pion и несовместимость с SDK делают слепое обновление рискованным.
- Этап 1.4 должен сразу реализовать `--advertise-ip`/`ROSTALK_ADVERTISE_IP` и
  проверить медиа с Windows-хоста по UDP; иначе dev-сценарий на Windows
  останется нерабочим.
- На этапе 7.1 повторить замеры на настоящем Linux и заполнить
  `docs/PERF.md`; текущие цифры — только ориентир.

## Как воспроизвести

```powershell
cd spikes/embed-livekit
docker compose up --build -d          # шлюз + встроенный LiveKit
powershell -File bench/measure.ps1 -Publishers 9 -Subscribers 1 -DurationSec 60 -Label "10"
```

Ключи и отпечаток печатаются в логах контейнера. Подробности — в
`spikes/embed-livekit/README.md`.
