# ADR 0033. Переименование Hearth → RosTalk

- **Статус:** принято (этап P19, решение владельца от 2026-11-25)
- **Дата:** 2026-11-25
- **Связано:** ADR 0019 (обновление клиента), ADR 0021 (установка сервера),
  ADR 0026 (GitHub Releases), ADR 0034 (публичный репозиторий)

## Контекст

Проект выходит в открытый код в публичном репозитории
`github.com/v4dikos1/RosTalk`. До этого продукт назывался Hearth, релизы
публиковались в приватном репозитории. Владелец выбрал полный ребрендинг:
одно имя в репозитории, бинарниках, установщиках, протоколе и интерфейсе.

Имя Hearth было не только в текстах, но и в идентификаторах, которые хранят
состояние пользователя: идентификатор Tauri (`dev.hearth.desktop` →
`%APPDATA%`), служба Credential Manager с приватным ключом, магия файла
экспорта личности, схема ссылок `hearth://`, каталоги и юнит сервера
(`/var/lib/hearth`, `hearth-server.service`), файл базы `hearth.db`,
переменные `HEARTH_*`, прежнее имя Go-модуля.

## Решение

1. **Имена.** Hearth → RosTalk во всём коде, сборке и документации:
   `rostalk.exe`, `rostalk-server`, `rostalk-server-setup`, `rostalkctl`,
   `rostalk-sign`, крейты `rostalk-*`, пакет протокола `rostalk.v1`
   (`proto/rostalk/v1`), Go-модули `github.com/v4dikos1/RosTalk/...`,
   переменные `ROSTALK_*`, схема `rostalk://`, идентификаторы
   `dev.rostalk.desktop`, `dev.rostalk.server-setup`, `dev.rostalk.hosting`,
   репозиторий релизов по умолчанию `v4dikos1/RosTalk`. Исторические записи
   (журнал приёмки, план, отчёты приёмки) не переписываются.
2. **Протокол.** Пакет `hearth.v1` → `rostalk.v1`. В контракте нет
   `google.protobuf.Any` и gRPC-сервисов, сообщения ходят по WebSocket без
   имён типов, поэтому бинарный wire-формат не меняется: старые серверы и
   клиенты совместимы с новыми. `buf breaking` по правилам FILE видит
   переименование как удаление файлов, поэтому в ветке этапа сравнение идёт с
   `p19-proto-baseline` — `main` с тем же механическим переименованием. Чистый
   проход доказывает, что кроме имени в контракте ничего не изменилось. После
   вливания база — снова `main`.
3. **Криптография не меняется.** Подпись входа — `nonce || server_id` без
   строкового контекста, подпись релиза — по байтам `SHA256SUMS`. Ключ
   релиза, ключ апдейтера (minisign, `pubkey` в `tauri.conf.json`) и TLS
   серверов остаются прежними.
4. **Совместимость клиента** (`crates/platform/src/legacy.rs`):
   - при первом старте личность копируется из службы `dev.hearth.desktop`,
     а `%APPDATA%\dev.hearth.desktop` (серверы, настройки) — в новый каталог,
     если там пусто. Старое не удаляется: им владеет деинсталлятор старого
     клиента, а откат находит его на месте;
   - импорт личности принимает файлы с магией `HEARTHID` (заголовок
     аутентифицирован как записан); новые файлы — `ROSTALID`;
   - ссылки `hearth://join?...` принимаются при вставке. Обработчик
     `hearth://` в реестре не регистрируется: деинсталлятор старого клиента
     удалил бы его ключ;
   - установщик сервера переносит закреплённые SSH-ключи хостов
     (`dev.hearth.server-setup`). Запомненные SSH-пароли не переносятся:
     Credential Manager не даёт перечислить записи, мастер спросит заново.
5. **Совместимость сервера** (`server/internal/legacy`):
   - `hearth.db` (+ `-wal`, `-shm`) переименовывается в `rostalk.db` при
     старте `run`, `invite` и `backup`; операция идемпотентна, дозавершает
     прерванный запуск и ничего не перезаписывает;
   - `restore` принимает архивы со старым именем базы;
   - переменные `HEARTH_*` читаются, если не задана `ROSTALK_*`, с
     предупреждением в лог один раз;
   - `install.sh` на хосте со старой установкой останавливает и выключает
     `hearth-server`, переносит `/var/lib/hearth` → `/var/lib/rostalk`,
     передаёт файлы новому системному пользователю и оставляет старые бинарник
     и юнит как `*.hearth-old` для ручного отката;
   - мастер установки находит старую установку и останавливается с
     инструкцией обновить её один раз через `install.sh`: его резервная копия
     и обновление работают только с новыми путями.
6. **Ключи на машине сборки** ищутся сначала в
   `%USERPROFILE%\.rostalk\release\`, затем в старом `…\.hearth\release\`.
   Личные пути из скриптов убраны.

## Последствия

- Клиенты 0.2.0 не обновятся сами: их апдейтер смотрит в приватный
  репозиторий. Переход ручной: поставить RosTalk, запустить один раз
  (личность и серверы перенесутся), затем удалить Hearth **с сохранением
  данных**, если удаление предлагает выбор, или в любом порядке после первого
  запуска RosTalk.
- RosTalk ставится рядом с Hearth как отдельное приложение (новый
  идентификатор), а не поверх.
- Серверы на старом имени продолжают работать с новыми клиентами без
  обновления; при обновлении через `install.sh` данные переносятся.
- Слой совместимости (`legacy`) удаляется не раньше, чем все известные
  установки перейдут на RosTalk; удаление — отдельным решением.
