# ADR 0006. Локальный прокси сигналинга LiveKit с пиннингом сертификата

- **Статус:** принято (этап 2.3)
- **Дата:** 2026-11-20
- **Связано:** ADR 0001 (TLS без домена), ADR 0002 (голосовой движок)

## Контекст

Сервер RosTalk использует приватный CA и самоподписанный лист: клиент
доверяет серверу по отпечатку листа из ссылки-приглашения (`fp`), а не через
Web PKI (ADR 0001). Control-соединение на Rust проверяет `fp` само.

Медиа-сигналинг идёт в LiveKit через тот же шлюз `wss://<host>:7443/rtc`.
Крейт `livekit` 0.12 (через `livekit-signaling` 0.3) создаёт TLS-соединение
сам и проверяет цепочку по системному хранилищу. Хука для своего
верификатора или пиннинга листа в API нет:

- `RoomOptions`/`SignalOptions` не принимают TLS-конфигурацию;
- фичи `rustls-tls-native-roots` и `rustls-tls-webpki-roots` выбирают только
  источник корневых сертификатов;
- на Windows `rustls-native-certs` читает системное хранилище, а не
  `SSL_CERT_FILE`, поэтому трюк из спайка (ADR 0002) там не работает;
- добавлять приватный CA в системное хранилище без согласия пользователя
  нельзя, а отключать проверку сертификата — нельзя тем более.

## Решение

Голосовой движок поднимает локальный прокси сигналинга на loopback:

```text
livekit SDK ── ws://127.0.0.1:<port> ──► прокси ──► wss://<host>:7443/rtc
                                          │
                                          └─ SHA-256 листа == fp из ссылки
```

- Прокси слушает только `127.0.0.1` на случайном порту.
- На каждый входящий WebSocket он открывает TLS-соединение к шлюзу с
  `rustls` и собственным `ServerCertVerifier`: принимается ровно один лист,
  SHA-256 которого совпадает с `fp`. Подпись handshake проверяется штатным
  `ring`-провайдером; цепочка и имя хоста намеренно не проверяются, потому
  что сертификат самоподписанный.
- Токен доступа идёт внутри TLS-туннеля и в логи не попадает; URL шлюза тоже
  не логируется.
- Медиа (ICE/DTLS/SRTP) через прокси не идёт: только сигналинг.
- Прокси живёт ровно столько, сколько медиа-сессия; при смене канала или
  переподключении создаётся новый.

`MediaCredentials` ядра дополнены полем `tls_fingerprint` (отпечаток листа из
активной ссылки). Это не секрет и по IPC в UI не передаётся.

## Последствия

- Медиа-сигналинг аутентифицирует сервер тем же `fp`, что и control-плоскость;
  отключения проверки сертификата нет.
- Появляется один локальный TCP-порт на время звонка и небольшой прокси
  (две задачи на соединение). Задержка сигналинга — доли миллисекунды,
  на медиа не влияет.
- Крейт `livekit` не умеет ходить через HTTP-прокси для WSS, поэтому
  корпоративные proxy-настройки не подхватываются; для self-hosted сценария
  это не требуется.
- Если LiveKit SDK на ошибке сам вызывает HTTP `validate` по исходному URL,
  он ходит напрямую и без пиннинга; это диагностический запрос, который не
  влияет на установленное соединение. В логах он выглядит как TLS-ошибка.
- Когда у сервера появится домен и Web PKI (режим `--domain`), прокси можно
  оставить для пиннинга или отключить; API движка от этого не меняется.
