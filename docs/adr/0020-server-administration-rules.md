# 0020. Администрирование: `manage_server` вне каналов, выдача ролей и HTTP-токены

Дата: 2026-11-21. Статус: принято для этапа 3.2.

## Контекст

Ревью 3.1 (`docs/REVIEW.md` §26) оставило два вопроса к этапу 3.2:

- назначение роли с правами выше актора: `Assign` проверял только позицию, но
  не `canGrant`, поэтому модератор мог выдать нижнюю роль с правом, которого у
  него нет;
- `manage_server` можно было deny/allow оверрайдом канала: дизайн 4.4 говорит
  «`manage_server` обходит всё», а оверрайд мог как отнять администратора в
  канале, так и выдать обычному участнику полные права в одном канале.

Этап 3.2 добавляет HTTP API с bearer-токенами: токен действует как одна роль.
Нужно было решить, где считаются права токена и как выдавать токен, не
дублируя правила.

## Решение

1. **`manage_server` определяется только объединением ролей.** В
   `perms.Effective` бит `manage_server` вырезается из `allow` и `deny`
   оверрайдов. Если он есть в ролях, субъект сразу получает `AllMask` во всех
   каналах; если его нет, оверрайд не может его выдать. Это соответствует
   формулировке дизайна и убирает оба нежелательных исхода.
2. **Нельзя выдать роль с правами, которых нет у актора.** `roles.Assign`
   дополнительно вызывает тот же `canGrant`, что создание и правка роли.
   Администратор (`manage_server`) по-прежнему может всё. Остальные выдают
   только подмножество своих прав.
3. **HTTP-токен — это роль, а не пользователь.** Токен хранит `role_id`;
   аутентификация читает `api_tokens` на каждом запросе (хеш SHA-256), берёт
   живую роль из `internal/roles` и строит `perms.Subject` с отрицательным
   синтетическим id. Проверки идут через `control.Plane.Apply`, то есть тем же
   кодом, что `AdminAction`; аудит получает `actor_id = 0` и
   `actor_name = "api:<имя>"`. Удаление роли оставляет токен валидным, но
   бесправным (403).

HTTP API — отдельный пакет `internal/httpapi`; он не реализует ни одной
проверки прав сам. `control.Plane.Apply` — единственная точка входа, поэтому
протокол, клиент и HTTP API не расходятся.

## Последствия

- Оверрайд канала больше не влияет на `manage_server`; старые строки в
  `channel_overrides` с этим битом игнорируются. Миграция не нужна.
- Модератор больше не может назначить заранее созданную роль с чужим правом;
  чтобы выдать её, нужно иметь это право самому.
- Токен нельзя «повысить» правкой роли задним числом без права на эту роль:
  создание токена проверяет иерархию через `CanManageRole`.
- Пароль сервера и plaintext токена не попадают ни в БД, ни в логи; в
  `ServerInfo` добавлен только флаг `password_set`, чтобы клиент показывал
  «пароль задан».
- OpenAPI (`docs/openapi.yaml`) и примеры (`docs/api.md`) — часть контракта
  3.2 и должны меняться вместе с `internal/httpapi`.
