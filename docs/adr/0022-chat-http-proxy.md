# ADR 0022. Чат: HTTP через loopback-прокси, токен сессии и вложения

- **Статус:** принято (этап 4.1)
- **Дата:** 2026-11-21
- **Связано:** ADR 0001 (TLS без домена), ADR 0004 (идентификатор сервера), ADR 0006 (WS-прокси сигналинга)

## Контекст

Дизайн (4.3) требует, чтобы WebView не ходил к серверу напрямую: сервер
использует самоподписанный лист, а пиннинг живёт в Rust-ядре. Для истории,
загрузки и просмотра вложений нужен HTTP, а не WebSocket. В протоколе
управления уже есть одно соединение с сессией, но у него нет HTTP-токена.

Нужно было решить четыре вопроса:

1. чем WebView аутентифицируется в HTTP-запросах, если токенов API (3.2) у
   обычного пользователя нет;
2. какие маршруты вообще доступны через прокси, чтобы страница не получила
   универсальный клиент к серверу;
3. как проверять права на вложения и личные сообщения;
4. как хранить и удалять файлы, чтобы расширение и имя не влияли на тип.

## Решение

### Токен HTTP-сессии

`Welcome` получает аддитивные поля `http_token` и
`http_token_expires_in_seconds`. Сервер выдаёт случайный 32-байтный токен при
каждом успешном рукопожатии, хранит только его SHA-256 в
`internal/sessionauth` и отзывает при завершении сессии. Токен живёт в
памяти ядра, в `Welcome` и в заголовке `Authorization` запросов прокси; он не
попадает ни в UI, ни в логи, ни в `localStorage`. Повторное подключение
выдаёт новый токен, старый отзывается вместе с сессией.

HTTP API принимает такой токен как пользователя (не как роль) и проверяет
права тем же `internal/perms`, что WebSocket. Токены API из 3.2 по-прежнему
действуют как роль и к чату не допускаются: сообщение принадлежит
пользователю.

### Loopback-прокси

Ядро поднимает HTTP-сервер на `127.0.0.1:<случайный порт>` (ADR 0006 уже
делает это для WSS-сигналинга). Каждый запрос обязан нести
`X-RosTalk-Proxy-Token` — случайный токен процесса; для `<img>` разрешён
`?pt=` (заголовки у картинки поставить нельзя). Разрешены ровно три
маршрута:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/chat/history` | страница истории по курсору |
| POST | `/chat/attachments` | загрузка файла |
| GET | `/chat/attachments/{id}` | чтение вложения |

Прокси открывает TLS-соединение к серверу с тем же `PinnedVerifier`, что и
control plane: принимается ровно лист с отпечатком из активной ссылки. Токен
сессии добавляется в `Authorization` уже на стороне ядра. Общего
forward-маршрута нет, поэтому скрипт страницы не может использовать прокси
как открытый клиент.

CSP Tauri дополнен `http://127.0.0.1:*` в `connect-src` и `img-src`; других
сетевых источников у WebView нет.

### Сообщения, курсоры и непрочитанное

- Сообщение принадлежит либо каналу, либо паре пользователей. В wire-форме
  `recipient_id` — фактический получатель личного сообщения; клиент сам
  выводит собеседника (`sender_id` для входящего, `recipient_id` для своего).
- Курсор истории — base64 от `v1:<ключ разговора>:<id>`; чужой курсор
  отклоняется, порядок всегда по возрастанию id.
- Маркер прочтения хранится на пользователя и разговор. Непрочитанное и
  упоминания считаются SQL-запросами по сообщениям новее маркера, поэтому
  счётчики не расходятся с историей. Снимок при входе содержит счётчики.
- Упоминания (`@ник`) разрешаются на сервере по списку пользователей; ник
  может содержать пробелы, поэтому выбирается самое длинное совпадение с
  границей слова. Упоминать можно только тех, кто видит канал, или
  собеседника в личке.

### Права

Добавлены права `send_messages` (50), `attach_files` (51),
`manage_messages` (52). Миграция `0005_chat.sql` выдаёт `send_messages` и
`attach_files` ролям Member, Moderator и Admin, `manage_messages` —
Moderator и Admin. Guest остаётся без права писать: его набор прав не
меняется. Для личных сообщений используется объединение прав ролей
(канал 0), потому что у лички нет канала с оверрайдами; это то же правило,
что у `SetNickname`.

Автор может править и удалять свои сообщения; `manage_messages` в канале
разрешает править и удалять чужие сообщения канала. В личных сообщениях
модерация не действует.

> Уточнено ADR 0025: `manage_messages` удаляет чужие сообщения, но не правит
> их. Правка — только автор.

### Вложения

Файл загружается до отправки сообщения (claim при `ChatSend`), поэтому у
вложения есть владелец и срок годности; невостребованные файлы удаляются
через час. Тип определяется `http.DetectContentType` по первым байтам, а не
по имени или расширению:

- принимаются PNG, JPEG, GIF, WebP, PDF, обычный UTF-8 текст и
  `application/octet-stream`;
- HTML, SVG, XML, архивы и любой текст, начинающийся с `<`, отклоняются;
- имена файлов санируются и используются только для отображения; на диске
  файл называется случайным hex-именем;
- отдача: `X-Content-Type-Options: nosniff`, `Content-Security-Policy:
  default-src 'none'; sandbox`, `Content-Disposition: inline` только для
  растровых картинок, иначе `attachment`;
- лимит размера, квота диска и срок хранения — в таблице `settings`
  (`max_attachment_bytes`, `attachment_quota_bytes`,
  `message_retention_days`); меняются через `rostalk-server admin settings
  set`. Sweeper работает пакетами по 200 сообщений и не держит транзакцию
  на всю историю;
- удаление сообщения удаляет строки вложений и файлы.

## Последствия

- Прокси существует только пока есть сессия; после реконнекта координаты
  прокси меняются, UI получает их через IPC `chat_proxy()`.
- HTTP-часть использует тот же пиннинг, что и WSS; отключения проверки
  сертификата нет. Корпоративные HTTP-прокси не поддерживаются (как и в
  ADR 0006).
- Токен сессии видит только ядро; утечка через UI или лог исключена. Он
  отзывается при завершении сессии, кике и бане (через закрытие сессии).
- Вложения лежат в `<data>/files` рядом с базой; бэкап 6.1 должен включать
  каталог. Квота считается по строкам `attachments`, а не по `du`.
- История не реплицируется в снимок: после входа клиент запрашивает
  последнюю страницу через прокси, а живые сообщения приходят событиями.
- Ограничение частоты отправки — 5 сообщений подряд, затем 1 за 500 мс
  (120/мин) на пользователя; параметр не вынесен в настройки, потому что
  дизайн 8 требует лимит, но не даёт оператору ручку.
