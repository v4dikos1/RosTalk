# ADR 0008. Вход по IP без инвайта: TOFU и закладки

- **Статус:** принято (этап 2.3.1, блок C)
- **Дата:** 2026-11-20
- **Связано:** дизайн 4.2, 4.3; ADR 0001, ADR 0004, ADR 0006

## Контекст

До 2.3.1 войти в RosTalk можно было только по ссылке-приглашению
`rostalk://join?host=…&fp=…&invite=…`. Ссылка решает две задачи сразу: она
передаёт адрес и отпечаток TLS-листа (`fp`), поэтому клиент пинит сертификат
(ADR 0001), а инвайт открывает вход на сервере с режимом `invite`.

Пользователю нужен второй способ: ввести `host:port`, пароль сервера (если он
задан) и ник — без ссылки. У этого способа нет канала, по которому пришёл бы
`fp`. Просто «принять любой сертификат» нельзя: это отключает единственную
проверку подлинности сервера без домена и молча ослабляет ADR 0001.
Одновременно выяснилось, что закладки хранятся по отпечатку сертификата: после
переустановки сервера или смены сертификата появляется второй сервер-призрак, а
`server_id` из ADR 0004 с новым отпечатком не сверяется.

## Решение

### Два способа входа, один wire-протокол

1. **Ссылка-приглашение** — как раньше. `fp` и инвайт берутся из ссылки; `fp`
   считается подтверждённым по внешнему каналу (админ прислал ссылку).
2. **Прямой вход** — `host:port` + пароль сервера (если задан) + ник. Инвайта
   нет; на сервере это работает в режимах `password` и `open`, а для уже
   известного ключа — и в режиме `invite` (сервер узнаёт пользователя по
   `public_key`).

Контракт `proto/rostalk/v1` не меняется: `Hello.invite` и так может быть пустым,
пароль сервера уже есть в `Hello.password`. Пароль канала — отдельное поле
`JoinChannel.password`; пароли не пересекаются, не хранятся и не логируются.

### Как клиент получает отпечаток: TOFU с явным подтверждением

Первый прямой вход идёт в два шага:

1. **Проба сертификата.** Клиент открывает TCP и TLS к `host:port` и сразу
   закрывает соединение, не отправляя `Hello`, публичный ключ, пароль или
   инвайт. Верификатор только записывает SHA-256 предъявленного листа. Он
   по-прежнему отвергает CA-сертификат в роли листа (ловушка ADR 0001:
   Go принимает такой сертификат, rustls — нет).
2. **Подтверждение.** UI показывает SHA-256, режим доверия и — если сервер уже
   был в закладках — предупреждение о смене сертификата. Пользователь
   подтверждает отпечаток (TOFU, как host key в SSH) или вставляет `fp` вручную
   из консоли сервера: ручной ввод — это отдельное поле в том же диалоге, и он
   считается подтверждением (источник отпечатка — человек, а не сеть). Введённый
   вручную отпечаток разрешает заменить сохранённый, но TLS всё равно сверяет
   его с предъявленным листом.

Только после подтверждения клиент подключается с этим отпечатком, и обычный
`PinnedVerifier` проверяет его при каждом рукопожатии. Приёмка «какой угодно
сертификат» существует только внутри пробы, которая ничего не отправляет, и
живёт до первого подтверждения. Отключения проверки TLS нет.

Для домена (`--domain`, обычный Web PKI) отпечаток не пинится: сертификат
Let's Encrypt обновляется, и пиннинг сломал бы вход. Проба в этом режиме
проверяет цепочку и имя по Web PKI, а отпечаток сохраняется в закладке только
для медиа-прокси (ADR 0006) и отображения.

### Смена сертификата не проходит молча

Закладка хранит отпечаток, с которым сервер был сохранён. Прямой вход с другим
отпечатком для того же `host:port` возвращает `serverCertificateChanged` и
**не отправляет ничего на сервер**, пока пользователь не подтвердит новый
сертификат в диалоге. Подтверждение передаётся в ядро отдельным флагом
`acceptNewCertificate`; оно разрешает заменить сохранённый отпечаток, но не
обходит TLS: если предъявленный лист не совпадает с подтверждённым, рукопожатие
падает с `tlsFingerprintMismatch`.

Ссылка-приглашение остаётся внешним подтверждением: новая ссылка от админа
несёт новый `fp` и заменяет сохранённый. Проверка `server_id` (ADR 0004)
выполняется в обоих случаях и по-прежнему блокирует смену ключа сервера.

### Закладки по хосту, а не по отпечатку

`servers.json` версии 2 хранит `id = host:port`, а также `host`, `fingerprint`,
`mode`, `login` (`invite`/`direct`), `nickname`, `server_id` и каноническую
ссылку без инвайта. Смена сертификата заменяет запись, а не создаёт вторую.
Файл версии 1 (id = отпечаток) мигрируется при чтении и переписывается в новом
формате; активный сервер находится по отпечатку.

Повторный вход по закладке идёт по канонической ссылке без инвайта: известному
ключу инвайт не нужен, а `fp` в ссылке — тот, который пользователь уже
подтвердил.

### Ник

Ник спрашивается при первом входе, если он ещё не задан, и хранится в ядре в
`profile.json` (там только ник — ни ключей, ни паролей, ни токенов) и в
закладке сервера. При входе приоритет такой: явно введённый ник → ник закладки
→ ник профиля. `set_nickname` при активном соединении отправляет `SetNickname`
серверу и сохраняет принятый ник локально; без соединения (минимальный экран
профиля) он обновляет только локальный профиль. Сервер остаётся источником
истины, пока клиент подключён.

### Сервер

Режим входа и пароль сервера задаются флагами `--login-mode`
(`invite`/`password`/`open`) и `--server-password` (или
`ROSTALK_LOGIN_MODE`/`ROSTALK_SERVER_PASSWORD`). Пароль хешируется argon2id в
таблицу `settings` и никогда не пишется в лог; флаг только заполняет настройку,
дальше она живёт в базе. `--server-password` без `--login-mode=password` —
ошибка запуска.

## Последствия

- Первый прямой вход уязвим к MITM в той же мере, что и первый SSH-коннект:
  подмена возможна до того, как пользователь сверил отпечаток. Поэтому UI
  показывает SHA-256 крупно и предлагает сверить его с консолью сервера
  (`certificate_fingerprint` печатается при старте), а не только нажать
  «ОК». Дальнейшие входы защищены пином.
- Сервер без домена обязан печатать отпечаток листа в консоли; это уже так
  (этап 1.2), менять формат не нужно.
- Диалог подтверждения — часть 2.3.1; полноценный первый запуск с проверкой
  микрофона остаётся за 2.4.
- `servers.json` получил версию 2 и миграцию; откат на клиент 2.2 потребует
  удалить файл (данные — только закладки, ключ лежит в хранилище).
- Прямой вход в режиме `invite` для нового ключа отклоняется сервером
  (`inviteInvalid`); UI показывает это как «нужна ссылка-приглашение».

## Альтернативы

- **Принимать любой сертификат при прямом входе.** Просто, но полностью
  отключает проверку подлинности сервера без домена и превращает MITM в
  штатный сценарий. Отклонено.
- **Доверять CA сервера вместо листа.** Go такое примет, rustls отклонит
  (`CaUsedAsEndEntity`); кроме того, тогда любой лист, подписанный этим CA,
  считался бы тем же сервером. Отклонено (см. ADR 0001).
- **Только ручной ввод `fp`.** Безопаснее против MITM, но требует, чтобы
  пользователь каждый раз лез в консоль сервера; для «друзей и домашнего
  сервера» это лишний барьер. Оставлен как вариант внутри TOFU-диалога.
- **Пинить сертификат и для домена.** Ломается на обновлении Let's Encrypt.
  Отклонено.
