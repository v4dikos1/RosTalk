# ADR 0018. Выдача ролей и неприкосновенный `manage_server`

- **Статус:** принято и реализовано в 3.2 (ADR 0020)
- **Дата:** 2026-11-21
- **Связано:** дизайн 4.4, ADR 0016; `docs/REVIEW.md` §26

## Контекст

В 3.1 модель прав реализована так: эффективные права — объединение ролей →
deny канала → allow канала; `manage_server` обходит проверки; иерархия — по
позиции старшей роли. Ревью выявило две неоднозначности:

1. **Назначение роли.** `Assign` проверяет иерархию позиций, но не проверяет,
   что актор вправе выдать права этой роли. Модератор с `manage_roles` может
   назначить нижнюю роль, у которой есть, например, `ban`, хотя сам этого права
   не имеет. Правило «нельзя выдать право, которого нет у тебя» уже действует
   для создания/изменения роли и для allow-оверрайдов, но не для назначения.
2. **`manage_server` в оверрайдах.** `Effective` сначала применяет deny/allow
   канала и только потом проверяет `manage_server`. Поэтому deny канала может
   «отключить» администратора в канале, а allow — выдать Member все права в
   канале. Дизайн 4.4 говорит: «`manage_server` обходит всё», что читается как
   «если он есть в объединении ролей, оверрайды его не отменяют».

## Решение

1. **Назначение роли требует права выдать её права.** `Assign` (и выдача роли
   инвайтом) дополнительно проверяет `canGrant(actor, role.Permissions)`.
   Актор с `manage_server` освобождён. Иерархия по позиции сохраняется.
2. **`manage_server` считается только по объединению ролей.** Канальные
   оверрайды не могут ни добавить, ни отнять `manage_server`. Если он есть в
   объединении ролей, эффективные права в любом канале — все; если нет —
   оверрайды работают как обычно. В снимке `effective` для такого актора
   содержит все права.
3. Сервер остаётся единственным местом проверки; UI лишь скрывает недоступное.
   Обе правки покрываются табличными тестами (`perms`, `roles`) и интеграцией:
   модератор не может выдать роль с чужим правом; deny `manage_server` в канале
   не мешает администратору; allow `manage_server` модератору не выдаёт.

## Последствия

- Небольшое ужесточение для модераторов: роль с правами выше их собственных
  теперь нельзя назначить, даже если она ниже по позиции. Это осознанно:
  иначе иерархия обходится через заранее созданную роль.
- Администратор больше не может быть «заперт» в канале оверрайдом; при этом
  оверрайды для обычных ролей не меняются.
- Совместимость wire не меняется: это серверная логика и тесты.
- Откат: вернуть прежние проверки в `perms.Effective`/`roles.Assign` и снять
  соответствующие тесты; данные не затрагиваются.

## Реализация

Отдельный небольшой коммит (3.1a) после 3.2: `server/internal/perms/perms.go`,
`server/internal/roles/roles.go`, тесты и интеграционный сценарий. До этого
поведение 3.1 остаётся как есть и зафиксировано в `docs/REVIEW.md` §26.
