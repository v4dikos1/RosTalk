# 0023. Навигация WebView ограничена origin приложения

Дата: 2026-11-22
Статус: принято

## Контекст

Сообщения чата и уведомления об ошибках показывают ссылки как `<a target="_blank">`.
В Tauri 2 запрос нового окна без обработчика отклоняется (`NewWindowRequested` →
`SetHandled(true)`), а навигацию самого WebView никто не ограничивал. В результате
внешние ссылки не работали, но — что важнее — любая навигация на чужой origin
(в том числе из вставленного контента или ссылки, пришедшей с сервера) заменила
бы интерфейс приложения страницей в том же привилегированном WebView, рядом с IPC.

## Решение

1. Окно `main` создаётся кодом (`"create": false` в `tauri.conf.json`) в
   `ensure_main_window` — на старте и при пересоздании экономичным режимом, —
   чтобы к нему можно было прикрепить `on_navigation`.
2. `is_app_url` пропускает только origin приложения: `tauri://localhost`,
   `http(s)://tauri.localhost`; в debug-сборке дополнительно Vite
   (`http://localhost:1420`, `http://127.0.0.1:1420`). `about:blank` разрешён
   только как служебный первый документ WebView2. Всё остальное не загружается.
3. Окно создаётся одним путём, поэтому настройки безопасности (включая
   `disable_native_context_menu`) применяются и после выхода из экономного
   режима.

## Последствия

- Чужой origin не может занять привилегированный WebView и получить доступ к
  IPC, даже если в чат попала ссылка или HTML с сервера.
- Внешние ссылки в чате остаются видимым текстом: клик по ним не открывает
  браузер. Открытие в системном браузере потребовало бы нового Win32-вызова
  (`ShellExecuteW`) сверх белого списка «Античит-гигиены». По правилу проекта
  это делается только через отдельный ADR и живой прогон G7 с Vanguard, а не
  «попутно»; до такого решения ссылки не кликабельны.
- Ссылка из `Error.action_url` тоже не может увести WebView на чужой сайт.
- Сеть приложения не меняется: UI по-прежнему ходит только в IPC и локальный
  прокси.
