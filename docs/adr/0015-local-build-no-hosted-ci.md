# ADR 0015. Локальная сборка и приёмка без хостингового CI

- **Статус:** принято (решение владельца проекта, 2026-11-20)
- **Дата:** 2026-11-20
- **Связано:** гейты G1/G5, этапы 6.1/6.2, `docs/REVIEWER_PROMPT.md`,
  ADR 0001 (Docker Desktop для сервера), ADR 0012 (античит-линтер 2.3.3)

## Контекст

Проект ведёт один человек на одной Windows-машине. GitHub Actions не
используется, `gh` не авторизован, отдельные PR не нужны. При этом гейт G1
требовал зелёного job `windows-latest`, а процесс — обязательного PR. Из-за
этого этап 2.3 не мог быть принят, хотя локальные `make check`, release-сборка
MSVC и живой прогон проходили: единственным «доказательством» считался внешний
сервис, которого в проекте нет.

Хостинговый CI добавлял внешнюю зависимость без реальной пользы для
единственного продукта — Windows-клиента. Ручная проверка на живом железе всё
равно обязательна для звука, ввода и установщика, а её CI не заменяет.

## Решение

1. **Приёмка локальная.** Обязательный минимум перед влитием в `main`:
   `make check` полностью, `make build-client` (release MSVC), запуск
   release-`rostalk.exe` и живой сценарий этапа. Ревьюер выполняет это сам,
   не полагаясь на отчёт исполнителя.
2. **Гейт G1 переопределён.** Вместо «зелёный `windows-latest`» —
   «локальная release-сборка MSVC собирается и запускается; `make check`
   зелёный». G5 (установщик и обновление на чистой Windows) остаётся ручным
   гейтом.
3. **PR не обязательны.** Исполнитель работает в ветке
   `stage/<номер>-<кратко>`; ревьюер пишет вердикт в `docs/REVIEW.md` и вливает
   ветку в `main` сам. Push ветки — по желанию, для бэкапа.
4. **Файлы `.github/workflows` остаются** как справка и заготовка. Они не
   запускаются, не блокируют этапы и не являются доказательством. Если CI
   когда-нибудь понадобится, гейт G1 возвращается к исходной формулировке.
5. **Установка сервера** — двумя путями, оба без CI:
   - терминал на целевой Linux-машине/VM: `install.sh` из 6.1;
   - из интерфейса клиента: пользователь вводит адрес машины и учётные данные,
     клиент подключается по SSH и устанавливает сервер, затем показывает
     ссылку-приглашение. Требования к безопасности (хранение кредов, host key,
     отсутствие их в логах) и выбор SSH-библиотеки оформляются отдельным ADR в
     этапе 6.1/6.2.
6. **Обновление клиента** — вручную (скачивание новой сборки) или из интерфейса
   клиента: проверка версии по указанному источнику, скачивание подписанного
   пакета и перезапуск. Автообновление не должно прерывать разговор без
   подтверждения (этап 6.2).

## Последствия

Плюсы: нет зависимости от внешних сервисов; приёмка идёт на том железе, где
продукт реально работает; меньше бюрократии на этап.

Минусы и компенсация:

- нет автоматической проверки на чистой машине и второй ОС — регрессии
  Windows-специфики ловятся только локально; компенсируется тем, что ревьюер
  сам собирает release и запускает его на каждой ветке;
- «зелёный» статус подтверждается только локальным выводом — отчёт должен
  содержать команды и результат, а не слова;
- `make check` становится единственной страховкой контракта и генерации —
  ослаблять его или пропускать нельзя.

## Откат

Если появится внешний CI (или понадобится проверка на второй машине), вернуть
G1 в редакции «зелёный `windows-latest`»: workflow уже лежит в репозитории.
Остальные пункты (локальная приёмка, установка из клиента, обновление из UI)
от этого не зависят.
